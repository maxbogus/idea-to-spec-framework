# Сравнение с OpenSpec

> Часть A плана 2026-11-25. Факты об OpenSpec проверены 2026-11-25 по
> первоисточнику (github.com/Fission-AI/OpenSpec); характеристики без
> источника помечены `[не подтверждено]`. Ссылок на другие репозитории здесь
> нет намеренно: фреймворк самодостаточен.

## 1. Зачем сравнение

Два инструмента решают одну задачу с разных сторон: «идея → проверяемая
спецификация». OpenSpec даёт **дисциплину изменения** (дельта, архив, живая
спека), фреймворк — **дисциплину обнаружения** (роли, гейты, факт/гипотеза,
машинные проверки ID). Сравнение нужно, чтобы не дублировать чужое и не
потерять своё.

## 2. Что такое OpenSpec

| Утверждение | Источник |
|---|---|
| CLI-фреймворк для spec-driven workflow с AI-ассистентами, без API-ключей | github.com/Fission-AI/OpenSpec, 2026-11-25 |
| Уровень — **spec-anchored**: спека живёт вместе с фичей | там же |
| Структура: `openspec/specs/<capability>/` — живая спека; `openspec/changes/<id>/` — `proposal.md`, дельта требований, `design.md`, `tasks.md` | там же |
| Архив сливает дельту в живую спеку; история изменений остаётся в архиве | там же |
| Проверяемость структурная: `openspec validate` + граф артефактов | там же |
| 30+ поддерживаемых ассистентов, лицензия MIT | там же |

Ранее в отраслевых обзорах встречалось написание «open-spec» — это тот же
инструмент.

## 3. Оси сравнения

| Ось | Фреймворк «идея → спецификация» | OpenSpec |
|---|---|---|
| Вход | сырая идея as-is (одна строка) | существующая система + намерение изменения |
| Направление | discovery: потребность → требования → архитектура | change management: дельта к живой спеке |
| Уровень SDD | spec-first для нового продукта, spec-anchored при повторных прогонах | spec-anchored |
| Артефакты | 16 файлов прогона + 29 шаблонов диаграмм (base/extended/паки) | `proposal.md`, delta-spec, `design.md`, `tasks.md` |
| Жизненный цикл | этапы + гейты BA → SA → Spec | change → validate → archive |
| Дельта и архив | нет: каждый прогон — новый каталог `output/<run-id>/` | есть: дельта + слияние в живую спеку при архивации |
| Валидация | `check_run`, `check_dor`, `check-sync`, `check-cross-refs`, `check-ledger`, eval-контракты | `openspec validate` (структурная) |
| Трассировка | ID-граф: `P-*`, `J-*`, `UC-*`, `BR-*`, `FR-*`, `NFR-*`, `AC-*`, `T-*` | capability-папки + ссылки в дельте |
| Роли | 6 ролей + 2 субагента, форматы ответов в промптах | нет ролей: ассистент пользователя |
| Режимы работы | `auto` / `chat` / `hybrid` с лимитом вопросов | не формализованы |
| Факт vs гипотеза | обязательный маркер `[HYPOTHESIS]` + hallucination-log | не формализовано |
| Комплаенс | региональные чек-листы (GDPR, 152-ФЗ, PIPL, HIPAA), STRIDE | вне scope |
| Eval | promptfoo-контракты, `xfail(strict=True)`, целевые замеры | вне scope |
| Зависимости | файлы + опционально `uv`/`npm` | CLI, без API-ключей |

## 4. Что берём и что не берём

**Берём:**

- дельту как единицу изменения: спека не переписывается целиком;
- архив как историю намерения, а не только историю файлов;
- структурную валидацию до того, как спека попадёт в работу.

**Не берём:**

- отказ от ролей: без BA-gate и SA-gate требования теряют владельца;
- отказ от факт/гипотезы: это главный механизм против выдуманных чисел;
- capability-папки вместо ID-графа: ID проверяются машинно, папки — нет.

## 5. Как совмещать

Разделение по времени: фреймворк отвечает за **upstream** (что вообще
строим и почему), OpenSpec — за **downstream** (как менять уже работающую
систему).

| Шаг | Кто | Результат |
|---|---|---|
| 1 | фреймворк, режим `auto`/`hybrid` | `output/<run-id>/spec.md` + диаграммы + run-report |
| 2 | человек | подтверждает или отменяет допущения Q-* |
| 3 | OpenSpec | `openspec/changes/<id>/proposal.md` + delta-spec + `tasks.md` |
| 4 | OpenSpec | `validate` → реализация → `archive` (дельта сливается) |

Отображение артефактов:

| Фреймворк | OpenSpec |
|---|---|
| `business-requirements.md` (BR) | раздел «Why» в `proposal.md` |
| `functional-requirements.md` (FR + AC) | delta-spec, `## ADDED/MODIFIED Requirements` |
| `spec.md §9`, ADR | `design.md` |
| `traceability-matrix.md` + план | `tasks.md` |
| `validation-report.md`, `hallucination-log.md` | вход для ревью перед `validate` |

Правило границы: прогон фреймворка **read-only** для кода системы; изменение
живёт в `openspec/changes/`. Обратное тоже верно: OpenSpec не подменяет
discovery — он не умеет задавать вопросы за заказчика и не маркирует
допущения.

## 6. Ограничения сравнения

- OpenSpec проверен по репозиторию и README на 2026-11-25; поведение CLI на
  нестандартных структурах не измерялось.
- Число «30+ ассистентов» — заявление проекта, не независимый замер.
- Совмещение (§5) описано как процесс, а не как готовый коннектор: конвертера
  артефактов нет.
