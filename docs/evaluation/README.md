# Eval промптов — отчёты и находки

> Автоматическая проверка, что промпты работают так, как описано в
> `handout-index.md` и `prompts/rules.md`. Обвязка: `eval/`, `scripts/*.py`,
> `tests/`. Реальный прогон — на локальной модели через Ollama.

## Как запускать

```bash
make eval-setup   # один раз: uv sync + npm install
make eval-mock    # детерминированный replay без LLM (зелёный в CI)
make eval         # реальный прогон qwen3:8b, отчёт в docs/evaluation/
make test-eval    # pytest-контракты (mock + slow)
```

- Отчёт: `docs/evaluation/eval-qwen3-8b.json` (другой моделью —
  `make eval OLLAMA_MODEL=<тег>`, отчёт ляжет в `eval-<тег>.json`).
- Сводка: `scripts/summarize_eval.py`.
- Провалы модели фиксируются как `xfail(strict=True)` в
  `tests/test_eval_contract.py` (`KNOWN_MODEL_FAILURES`).

### Что означает `chat` и `hybrid` в наборе — и что не означает

**Диалог проверяется только там, где в контракте кейса есть сценарий
`dialogue`; остальные кейсы режимов `chat` и `hybrid` проверяют один ход в
режиме диалога.** Поэтому «7 кейсов в режиме chat» по-прежнему не значит
«диалог проверен полностью».

Что в обвязке есть (проверено по коду):

- `scripts/multi_turn_provider.py` — exec-провайдер, который сам вызывает
  Ollama по ходам: берёт вопрос из ответа роли, находит пару
  «вопрос → ответ» в сценарии кейса и передаёт следующий запрос с историей
  (`build_history`: реплики роли — `assistant`, ответы заказчика — `user`).
- Логика ходов общая с mock: `scripts/idea_to_spec/multi_turn.py::run_turns`
  вызывают оба провайдера, поэтому `eval-mock` воспроизводит то же поведение
  без модели (35/35 — по одному замеру на кейс после исправления выбора
  провайдера; до него каждый кейс шёл дважды и выходило 64/64).
- Ответ заказчика берётся из пары сценария; `question_contains` — фрагмент
  текста вопроса, а не точное совпадение (D015). Отвеченные пары
  пропускаются (F029), а если модель переформулировала вопрос — берётся
  первая неотвеченная пара по порядку (F030).
- Промпт следующего хода короткий (~1 КБ): роль, вход, все ответы заказчика
  и блок формата, извлечённый из промпта роли (D016, F027, F028).
- Когда сценарий исчерпан, follow-up содержит критерий остановки: условие
  «ответ закрыл последний невыясненный вопрос» + императив «Больше не
  задавай вопросов» + «поле questions — пустой список []» (D017, F026).

Что покрыто двумя многоходовыми кейсами (`metadata.dialogue = "true"`):

| Покрыто | Как проверяется |
|---|---|
| Второй ход: модель спросила → человек ответил → модель продолжила | провайдер передаёт историю и ответ заказчика |
| Реакция на ответ: величина из ответа заказчика, а не выдуманная | `dialogue_uses_customer_answer` |
| Отвеченный вопрос не висит открытым | `dialogue_closes_answered_question` |
| Критерий остановки: после последней пары новых вопросов нет | `dialogue_stops_when_answered` |
| Развилка в `hybrid` закрыта ответом заказчика | кейс ORCH-10 (`hybrid`) |
| Связка «вопрос → ответ» в артефактах прогона | `check_run.py`: у закрытого вопроса обязан быть источник «ответ заказчика», у открытого — нет |

Чего в покрытии **нет**:

| Не покрыто | Почему |
|---|---|
| Третий и последующие ходы с новыми темами | в сценарии кейса две пары; больше ходов ограничивает только предохранитель `MAX_TURNS` |
| Многоходовость у ролей PM / BA / SA | сценарии есть только у оркестратора (ORCH-09, ORCH-10) |
| Смена этапа после ответа на развилку | проверяется отсутствие вопросов, а не переход на другой этап |
| Два разных ответа на одну развилку → разные следующие шаги | нужен сценарий с альтернативами, его пока нет |

Единственный ручной многоходовый прогон — `output/chat-001` (18 вопросов,
источник «ответ заказчика»). Он не воспроизводим и в CI не запускается, но
его формат используется как образец для `open-questions.md`; связку
«вопрос → ответ» в артефактах теперь проверяет `check_run.py`.

### Этап 4: регрессия 0/23 — изоляция формата роли от общего контекста

Прогон после расширения промптов под SDLC/PDLC дал **0/23**. Причина
оказалась не в длине промпта, а в том, что модель брала идентификаторы из
общего контекста и подставляла их вместо полей своей роли: за прогон — 70
«чужих» ключей (`definition_of_ready`, `functional_requirements`,
`successMetric`, `paymentIntegration`, `skills_used`).

Измерено A/B-прогонами на `qwen2.5:7b` (23 кейса):

| Конфигурация | Результат |
|---|---|
| общие правила 7111 симв. + новый шаблон запроса | 5/23 |
| общие правила 2990 симв. (DoR/DoD, BDD, глоссарий вынесены) | 16/23 |
| минимальный шаблон запроса (текст HEAD + блок гайда) | 17/23 |

Отдельно изолирован вклад гайда оркестратора: при подключённом гайде — 0 из 5
кейсов оркестратора, без него — все пять с полным набором из восьми полей
(`mode`, `stage`, `completeness`, `gate`, `questions`, `artifacts`,
`assumptions`, `next`). Гайд перестал подключаться к запросу; его рабочие
части (триггеры режима, критерии выбора режима) перенесены в промпт роли,
сам файл остался справочником.

Что сделано:

| Находка | Исправление |
|---|---|
| в общих правилах перечислены имена полей чужих ролей (`status`, `risk`, `version`, `owner`, `priority`, `compliance`) | имена заменены словами; правило проверяет тест |
| DoR/DoD, формат BDD и глоссарий лежали в правилах для всех ролей | перенесены в промпты System Analyst, Project Manager и оркестратора |
| чек-листы гейтов были частью промпта — модель отвечала чек-листом | справочник `prompts/gate-checklists.md`, на запрос не подключается |
| глоссарий был частью промпта оркестратора — модель подставляла его термины | справочник `prompts/glossary.md`, на запрос не подключается |
| «Порядок этапов» оркестратора перечислял понятия («персоны», «тарифы», «use cases») — модель читала это как схему | в списке только названия этапов |
| в промптах встречались camelCase-токены — модель переносила их в ответ | токены убраны; проверяет тест |

Проверка статическая: `tests/test_prompt_context_isolation.py` ловит этот
класс дефекта без обращения к модели — чужие имена полей, артефакты чужих
ролей, справочники в промпте, camelCase-идентификаторы, бюджет общих
правил.

## Сравнение моделей

Модель в прогоне задаётся параметром:

```bash
make eval OLLAMA_MODEL=qwen3:8b
make eval-compare MODELS="qwen2.5:7b qwen3:8b mistral-nemo:12b"
```

Отчёты пишутся в `docs/evaluation/eval-<тег>.json`. Конфиг генерируется
`scripts/make_eval_config.py`: подставляется тег модели, а для моделей с
режимом рассуждений (`qwen3`, `deepseek-r1`, …) выключается `think` — для
eval нужен детерминированный JSON.

### Результаты (набор из 23 кейсов, RTX 5060 8 ГБ, 2026-11-23)

> **Устарело:** таблица измерена на наборе из **23 кейсов** (до расширения
> покрытия режимов). После расширения до 31 кейса рейтинг моделей не
> перезамерялся — перезамер требует прогона каждой модели на полном наборе.
> Числа ниже верны для старого набора.

| Модель | Параметры | VRAM | Пройдено | Доля | Время прогона |
|---|---:|---:|---:|---:|---:|
| `qwen3:8b` | 8.2B | 5.23 ГБ | **23/23** | 100% | ~30 мин |
| `qwen2.5:7b` | 7.6B | 4.68 ГБ | 18/23 | 78.3% | ~20 мин |
| `qwen3-4b-local` | 4.0B | 2.50 ГБ | 18/23 | 78.3% | ~14 мин |

Замеры в таблице — на промптах до двух правок: схемы персон и замены
лексического ассерта DISC-01 на структурный. После обеих `qwen3:8b` даёт
**23/23 (100%)**: BA-01 закрылся правкой схемы, NEG-01 — код-гейтом,
DISC-01 — структурной проверкой. Список `KNOWN_MODEL_FAILURES` пуст.

Три механизма закрыли регрессию 0/23: разделение контекста, код-гейт для
пустой идеи и структурные ассерты вместо лексических.

**Вывод: `qwen3:8b` — лучшая из доступных.** Разница с `qwen2.5:7b`
не в объёме знаний, а в дисциплине формата: `qwen3:8b` берёт значение полей
из входа (режим, этап) и отвечает полным набором полей, тогда как
`qwen2.5:7b` выбирает режим сам и отвечает `auto` вместо заданного `chat`.

Два наблюдения, важных для выбора:

- **Размер модели значим меньше, чем семейство.** `qwen3-4b-local` (4B)
  держит формат на уровне `qwen2.5:7b` (7.6B) — 78.3% против 78.3% — и
  занимает вдвое меньше VRAM. `mistral-nemo:12b` при 12B проигрывает 8B:
  на русском без файн-тюна она отвечает формально правильно, но не
  наполняет ответ (пустые `artifacts`, ответы по 146–247 символов).
- **Провал `mistral-nemo:12b` — не OOM.** Проверено по отчёту: 22 из 23
  ответов — валидный JSON, обрыва нет. Проблема в содержании, а не в
  памяти.

### Код-гейт: пустая идея не доходит до модели

Кейс `NEG-01-empty-idea` падал на всех семи измеренных моделях (3B–12B,
разные семейства): на пустом входе модель начинала прогон и писала
артефакты. Провал принадлежал не модели, а входу.

Теперь пустой вход отсекается кодом до вызова модели
(`scripts/idea_to_spec/input_gate.py`), а ответ даёт exec-провайдер
(`scripts/gated_provider.py`). Ответ детерминирован, токены не тратятся,
результат не зависит от модели на машине.

### Структурные ассерты вместо лексических

Контракт `DISC-01` требовал буквального слова «потребност» — которое ни
один промпт не предписывает. Все шесть моделей с валидным JSON описали
потребность правильно (в `jobs_to_be_done[].want`), но слово не употребляли.

Проверка заменена структурной (`scripts/idea_to_spec/semantic_check.py`):
потребность должна быть выражена, а решение — не выдано за потребность.
Одно правило используют и pytest-контракт, и assert promptfoo (через
`scripts/semantic_check_bridge.py`).

### Ledger и валидаторы

- `prompts/ledger/findings.jsonl` — измеренные факты; `decisions.jsonl` — решения.
  Формат проверяет `make check-ledger`.
- `scripts/check_cross_refs.py` — согласованность идентификаторов в схемах
  ролей (семантический аналог `check-refs`). Нашёл второй дефект класса
  BA-01: `functional_requirements[].source` в System Analyst требовал
  `BR-1`, хотя роль не объявляет `business_requirements`.

|---|---:|
| `qwen3:8b` + `qwen3-4b-local` | 21/23 |
| `qwen3:8b` + `qwen2.5:7b` | 21/23 |

| `qwen3:8b` + `qwen2.5:3b` | 20/23 |
| `qwen3:8b` + `mistral-nemo:12b` | 20/23 |

Перехлёст **устойчив, а не шум**: три повтора подряд на одном наборе дали
идентичный результат (`qwen3:8b`: BA-01 всегда FAIL, FC-01 и NEG-02 всегда
PASS; `qwen2.5:7b`: BA-01 и PM-02 3/3 PASS).

Но экономика роутера на 8 ГБ VRAM плохая: **две 8B-модели одновременно не
влезают** (`qwen3:8b` + `qwen2.5:7b` = 9.91 ГБ при лимите ~7.6 ГБ под
модели). Значит переключение = выгрузка и загрузка модели, ~10–20 с на
каждый переход.

**Вывод: роутер не нужен.** Причина единственного «неперекрытого» кейса
(`BA-01`) оказалась не в модели, а в промпте: `personas` были объявлены
массивом строк, хотя `jobs_to_be_done[].persona` ожидает идентификатор.
После правки схемы (`personas: [{"id": "P-1", ...}]`) кейс проходит на
`qwen3:8b` — одиночная модель закрывает его сама.

Итог: комбинирование моделей даёт +1 кейс и добавляет переключение
моделей на каждый вызов. Правильнее чинить промпт — это бесплатно.

Расхождения по кейсам (знак: `+` — прошёл, `-` — провалился):

| Кейс | qwen2.5:7b | qwen3:8b | command-r7b | mistral-nemo | qwen2.5:3b |
|---|:-:|:-:|:-:|:-:|:-:|
| `ORCH-02-chat-three-block-questions` | - | + | + | + | + |
| `NEG-02-no-gate-skip` | - | + | - | - | - |
| `BA-01-personas-jtbd` | + | - | + | - | - |
| `FC-01-three-statuses` | - | + | - | + | - |

Модели меньше 7B (`qwen2.5:3b`) держат формат заметно хуже: 11 провалов
из 23, теряет поля ролей целиком. `mistral-nemo:12b` при 12B параметров
проигрывает 8B-моделям — на русском отвечает хуже.

## Целевой замер вместо полного прогона

Правило владельца (2026-11-24): измерять только то, что оптимизируем, а не
весь набор. Полный прогон 35 кейсов на `qwen3:8b` — **14 минут** (замер
2026-11-26, concurrency 4; до исправления выбора провайдера тот же набор
занимал ~30 минут, потому что каждый кейс шёл через двух провайдеров);
целевое подмножество — в разы меньше.

```bash
make eval-target FILTER="mode=chat"        # только кейсы режима chat
make eval-target FILTER="dialogue=true"    # только многоходовые кейсы
make eval-target FILTER="scenario=ORCH"     # только сценарий ORCH
make eval-target FILTER="mode=chat,mode=hybrid"   # оба диалоговых режима
```

Фильтр — регулярное выражение по полю `metadata` кейса (`promptfoo
--filter-metadata`). Доступные поля: `id`, `role`, `scenario`, `kind`, `mode`.

Отчёт частичного замера пишется в `docs/evaluation/eval-<тег>.local.json` —
путь уже в `.gitignore`, поэтому подмножество не перезаписывает базовый отчёт
`eval-<тег>.json` и не попадает в git.

Финальный полный прогон (`make eval`) идёт отдельной волной: он обновляет
базовый отчёт и список `KNOWN_MODEL_FAILURES`.

дублирующихся разделов вместо новых.

### Что в итоге сработало

**ORCH-05 — подмена режима.** Причина оказалась не в формулировке промпта, а в
**дистанции**: «Режим работы: chat» стоял на позиции 65 запроса, а вход — на
позиции 9495. Между ними ~9.4 КБ промпта роли и правил, и режим забывался:
модель объявляла `auto`. Правка — не в промпте роли, а в eval-шаблоне: режим
продублирован рядом со входом (теперь в 168 символах после него). Оркестратор
при этом **сокращён** на 165 символов: разделы «Правила режимов», «Критерии
выбора режима» и «Триггеры режима» объединены в один.

**SA-03 — потеря хвоста формата.** Модель подставляла чужие имена полей:
`NFR` вместо `nonfunctional_requirements`, `questions` вместо
`open_questions`, `regional_checklist`. Источники указаны прямо в промпте:
тип поля `open_questions` (массив строк, а не таблица из

`FR-1`, `NFR-1` — значения поля `id`, а не имена полей верхнего уровня).

## Структурные проверки

Лексические ассерты (`must_contain` на конкретное слово) ненадёжны: слово
может быть не предписано промптом, и провал принадлежит ассерту, а не модели
(см. F007). Поэтому часть контрактов проверяется семантически — правилами в
`scripts/idea_to_spec/semantic_check.py`. Одно правило читают оба
потребителя: pytest и реальный прогон (через `scripts/semantic_check_bridge.py`).

| Проверка | Что ловит |
|---|---|
| `needs_separated` | решение выдано за потребность (в `jobs_to_be_done[].want`) |
| `mode_respected` | модель подменила заданный режим своим (у оркестратора) |
| `questions_three_blocks` | не каждый вопрос оформлен тремя блоками |
| `chat_keeps_open_questions` | роль в `chat` выдумала ответ заказчика вместо открытого вопроса |

В контракте кейса проверка задаётся полем `semantic_checks` (список). Поле
`semantic_check` (одна строка) остаётся рабочим для обратной совместимости.

Разделение по ролям существенно: у оркестратора в формате ответа есть поле
`mode`, поэтому для него работает `mode_respected`. У ролей BA/SA/PM/... поля
`mode` нет — объявлять режим роль не обязана, поэтому для них проверяется
поведение (`chat_keeps_open_questions`).

## Гейт свежести отчёта

`make check-eval-report` сверяет состав набора с отчётом реального прогона.
Раньше такого гейта не было, и устаревший отчёт обнаруживался только глазами
при чтении чисел. Гейт — human-review (не роняет сборку), как
`check-policy`: полный прогон идёт отдельной волной и не должен блокировать
работу над набором.

## Как добавить кейс

1. Добавить строку в `eval/cases/roles.jsonl`. Поля контракта: `id`, `role`,
   `scenario`, `kind`, `title`, `mode`, `input`, `expected_fields`,
   `must_contain`, `must_not_contain`, `mode_check`, `semantic_checks`,
   `requires_assumption_marker`, `boundary_markers`, `notes`. В `metadata`
   дублируются `id`, `role`, `scenario`, `kind`, `mode` — по `metadata`
   работает фильтр целевого замера (`--filter-metadata`).
2. Добавить «идеальный» ответ в `scripts/mock_provider.py` (по префиксу `id`)
   и маршрут в `build_answer`.
3. Обновить `tests/test_eval_contract.py`: размер набора, раскладка по
   сценариям. Порог покрытия режимов — в
   `test_eval_set_covers_dialogue_modes` (`chat` >= 4, `hybrid` >= 3).
4. Обновить `docs/evaluation/README.md` (состав набора).

Проверка без модели: `make eval-mock`.

## Как обновлять `KNOWN_MODEL_FAILURES`

`xfail(strict=True)` превращает внезапный проход в ошибку теста. Если модель
стала проходить кейс — уберите его из `KNOWN_MODEL_FAILURES`. Если новый кейс
провалился и это свойство модели, а не контракта — добавьте его в список с
комментарием-причиной.
