## 1. Назначение и scope

Лёгкий mobile-first CRM для соло-предпринимателей и малых B2B-команд
**[гипотеза о продукте]**: быстрый онбординг, воронка, напоминания, импорт
из таблиц, дашборд выручки.

**Входит:** контакты, воронка сделок, задачи/напоминания, импорт CSV,
дашборд, подписка, базовый экспорт/удаление ПДн.

**НЕ входит:** собственная телефония, полноценный маркетинг-автомейшн,
мобильные нативные приложения, ERP-интеграции **[границы — допущение; в брифе
не заданы]**.

## 6. Данные и безопасность

- Какие данные: аккаунт пользователя (email, имя), контакты клиентов (имя,
  телефон, email), сделки (этап, сумма), задачи, подписка. **[гипотеза]**
- Персональные: да — контакты клиентов и аккаунты; минимизация обязательна.
- Срок хранения: **[допущение]** не определён; право на удаление — FR-9.
- Минимизация: не собирать лишнее (GDPR/152-ФЗ by design).

**Сущности (источник для ER-диаграммы):**

- `USER` — аккаунт (id, email, name)
- `CONTACT` — клиент (id, user_id, name, phone)
- `PIPELINE` — воронка (id, user_id, title)
- `STAGE` — этап (id, pipeline_id, title)
- `DEAL` — сделка (id, contact_id, stage_id, amount)
- `TASK` — задача (id, user_id, deal_id, due_at)
- `SUBSCRIPTION` — подписка (id, user_id, plan, status)

## 9. Архитектура и процессы

> Источник для C4 (`c4-context/container/component/deployment`) и DFD
> (`dfd-context`, `dfd-level1..3`). Без этого раздела диаграммы не выводятся.

**Слои / компоненты (C4):**

- Presentation — PWA-клиент (веб + мобильный веб), **[допущение]** стек: React/TypeScript.
- Application — CRM API (контакты, сделки, задачи, дашборд, биллинг).
- Domain — модель воронки, сделок, задач, правил доступа.
- Infrastructure — PostgreSQL, объектное хранилище (экспорт), очередь уведомлений, платёжный адаптер, email/мессенджер-шлюз.

**Процессы (DFD уровень 1):**

1. Управление контактами (создание, импорт, экспорт/удаление).
2. Управление сделками и воронкой (этапы, переходы, дашборд).
3. Уведомления (задачи → очередь → мессенджер/email).
4. Биллинг (freemium-лимиты → оплата → активация подписки).

**Хранилища (DFD / ER):**

- D1 `CRM_DB` — PostgreSQL: USER, CONTACT, PIPELINE, STAGE, DEAL, TASK, SUBSCRIPTION.
- D2 `OBJECT_STORE` — файлы импорта/экспорта.
- D3 `QUEUE` — очередь уведомлений.

**Декомпозиция:** DFD L2 — процесс «2. Управление сделками и воронкой»
(создание/перемещение/закрытие); DFD L3 — под-процесс «2.2. Перемещение
сделки» (валидация перехода → запись → уведомление).

## 10. ADR

| ID | Решение | Контекст | Последствия |
|---|---|---|---|
| ADR-1 | PWA вместо нативных приложений на старте | mobile-first, ограниченный бюджет | быстрее релиз, но ограниченный доступ к нативным API |
| ADR-2 | PostgreSQL как основное хранилище | реляционные данные воронки | простые транзакции, но нужен контроль ПДн |
| ADR-3 | Платежи через внешнего провайдера (РФ) | нет своей инфраструктуры | зависимость от провайдера, выбор не сделан |
| ADR-4 | Разделение freemium/paid на уровне API-лимитов | монетизация | нужен учёт usage и graceful degradation |

**Условие пересмотра ADR** (`methods/decision-keeper.md`): если выбранный
сегмент уйдёт в enterprise и потребует нативных приложений или телефонии —
ADR-1 и scope пересматриваются.
