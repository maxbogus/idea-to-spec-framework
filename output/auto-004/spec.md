# Спецификация

> Прогон `auto-004`: требования к фреймворку v0.3. Описание репозитория
> использовано как AS-IS; требования выведены заново. Всё, что не следует из
> входной строки и описания, помечено как гипотеза или допущение.

## 1. Назначение и scope

Фреймворк превращает одну строку бизнес-идеи в проверяемую спецификацию:
роли проходят этапы, каждый этап закрывается гейтом, артефакты связаны ID, а
машинные проверки отвечают за согласованность и отсутствие секретов.

**Входит:** intake, бизнес-анализ, системный анализ, архитектура, валидация
(fact-check и критик), план, CJM, диаграммы, машинные гейты, eval-набор,
подключение и экспорт.

**НЕ входит:** собственная LLM, внешняя облачная LLM по умолчанию
**[допущение: Q-4]**, серверная часть, хранение в базе данных, веб-интерфейс,
платежи, автоматическое исправление требований за автора.

## 2. Use cases

См. `use-cases.md`: UC-1 прогон из строки, UC-2 BA-gate, UC-3 требования и

## 3. Функциональные требования

См. `functional-requirements.md`: FR-1…FR-16. Десять требований закрыты

(`approved`), пять остаются разрывами v0.3 (`draft`) и приняты как допущения

## 5. Интеграции

| Откуда | Куда | Контракт |
|---|---|---|
| Фреймворк | Локальная LLM (Ollama) | HTTP API, модель по умолчанию `qwen3:8b` [факт: `Makefile` §Eval] |
| Фреймворк | promptfoo | CLI, конфиг генерируется перед прогоном [факт: `Makefile` §Eval] |
| Фреймворк | mermaid-cli (mmdc) | CLI, рендер `.mmd` в PNG [факт: `scripts/render-diagrams.sh`] |
| Фреймворк | git | список отслеживаемых прогонов и версия промптов [факт: `scripts/list_runs.py`] |
| Фреймворк | файловая система | артефакты в `output/<run-id>/` [факт: `prompts/start.md` §Шаг 2] |

Внешняя облачная LLM — **не интеграция по умолчанию** [допущение]: решение
за Q-4, при включении требуется оценка трансграничной передачи.

## 6. Данные и безопасность

- **Классификация данных:** артефакты прогона — внутренние; входная идея и
  персоны могут содержать персональные данные — конфиденциальные; eval-кейсы —
  внутренние, без реальных персональных данных.
- **Data residency (локализация):** артефакты лежат в файловой системе
  репозитория; внешняя LLM запрещена по умолчанию **[допущение: Q-4]**, поэтому
  данные не покидают машину; исключение требует отдельного решения.
- **Срок хранения и удаление:** артефакты живут в репозитории до удаления
  каталога прогона командой `clean-run`; отдельного retention-таймера нет.
- **Шифрование:** на диске — средствами ОС и git-хоста; при передаче во
  внешнюю LLM — TLS. Собственного шифрования фреймворк не реализует.
- **Минимизация:** персоны синтетические; реальные контакты и адреса в
  артефакты не вносятся, скан фиксирует находки (FR-13).

### Сущности

- `RUN` — прогон (id, mode, started_at, status)
- `ARTIFACT` — артефакт (id, run_id, path, kind)
- `REQUIREMENT` — требование (id, run_id, level, status, owner, risk)
- `TRACE_LINK` — связь (requirement_id, task_id, test_ref, status)
- `GATE_RESULT` — результат гейта (id, run_id, gate, status, missing)
- `FINDING` — находка (id, run_id, kind, status, source)
- `EVAL_CASE` — кейс (id, scenario, mode, expected_contract)

### Threat model (STRIDE) для high-risk

| Угроза | Где | Мера |
|---|---|---|
| Spoofing | FR-5: подмена результата гейта | результат гейта пишется с версией чек-листа и владельцем |
| Tampering | FR-13: правка артефакта после скана | скан запускается в том же прогоне, что и публикация |
| Repudiation | FR-5: «гейт не запускали» | запись GateResult и run-report с временем |
| Information disclosure | FR-13: персональные данные в артефакте | блокирующий режим скана и human-review |
| Denial of service | FR-15: прогон без лимита | лимит токенов и времени с точкой остановки |
| Elevation of privilege | FR-14: инструкция во входе меняет правила | вход трактуется как данные, правила задаёт только промпт роли |

## 9. Архитектура и процессы

**Слои / компоненты (C4):**

- Presentation — точка входа `prompts/start.md` и роль оркестратора; интерфейс
  командной строки пакета.
- Application — роли PM, BA, SA, Architect, Designer, Project Manager;
  субагенты fact-check и requirements-critic.
- Domain — модель требований и трассировки: `P-*`, `J-*`, `UC-*`, `BR-*`,
  `FR-*`, `NFR-*`, `AC-*`, `T-*`.
- Infrastructure — шаблоны, скилы, скрипты гейтов, eval-обвязка, mmdc, git.

**Процессы (DFD уровень 1):**

1. Intake: входная строка, гейт пустого входа, бриф.
2. Business: персоны, JTBD, BR, MoSCoW, BA-gate.
3. System: UC, FR, NFR, диаграммы, SA-gate.
4. Validation: fact-check, критик, Spec-gate.
5. Plan и Design: traceability, риск-регистр, план, CJM.
6. Eval: mock-набор, реальный прогон, целевой замер, ledger.

**Хранилища (DFD / ER):**

- D1 `ARTIFACT_STORE` — каталог `output/<run-id>/`.
- D2 `EVAL_CASES` — `eval/cases/roles.jsonl` и конфиги.
- D3 `LEDGER` — `prompts/ledger/*.jsonl` с находками.

**Декомпозиция:** DFD L2 — процесс «4. Validation» (fact-check, hallucination
log, requirements-critic, Spec-gate); DFD L3 — под-процесс «4.1. Fact-check»
(собрать утверждения → найти цитату → понизить статус → записать в лог).

**Зоны доверия:** клиент — недоверенная зона (точка входа); рабочая станция
и репозиторий — доверенная зона (роли, гейты, eval, артефакты); внешние —
локальная LLM, mermaid-cli и git-remote; см. `diagrams/c4-deployment.mmd`.

**Disaster Recovery (RTO / RPO):**

| Компонент | RTO | RPO | Мера |
|---|---|---|---|
| Репозиторий фреймворка | 4 ч | 1 ч | git-remote и повторный clone [допущение] |
| Артефакты прогона | 4 ч | 24 ч | коммит каталога прогона или повторный прогон [допущение] |

## 10. ADR

| ID | Решение | Контекст | Статус | Рассмотренные альтернативы (Pros/Cons) | Последствия |
|---|---|---|---|---|---|
| ADR-1 | Поведение задают промпты, код отвечает только за проверки | Нужна переносимость и правки без сборки | Proposed | 1. Prompt-only (+ правки без кода, − формат плывёт)<br>2. Код-оркестратор (+ детерминизм, − стоимость и жёсткость) | Быстрые правки, но нужен eval и машинные проверки формата |
| ADR-2 | Артефакты — markdown-файлы, без базы данных | Нужны diff, ревью и переносимость | Accepted | 1. Файлы (+ diff и git, − нет запросов)<br>2. БД (+ запросы, − миграции и инфраструктура) | Трассировка проверяется скриптами, история — через git |
| ADR-3 | По умолчанию локальная модель, внешняя — по решению | Приватность и автономность прогона | Proposed | 1. Локальная (+ данные не уходят, − качество модели)<br>2. Облачная (+ качество, − трансграничная передача) | Нужен ответ Q-4; eval меряет именно локальную модель |
| ADR-4 | Гейты проверяются машинно на Python, а не моделью-судьёй | Проверки должны быть воспроизводимы | Accepted | 1. Скрипты (+ детерминизм, − не всё формализуемо)<br>2. LLM-судья (+ гибкость, − нестабильность и стоимость) | Часть чек-листов остаётся человеческой (FR-5) |
| ADR-5 | Скилы — каталоги с SKILL.md и реестром | Нужны переиспользование и проверка синхронизации | Accepted | 1. Каталоги (+ переиспользование, − больше файлов)<br>2. Один справочник (+ компактность, − конфликты правок) | check-sync держит реестр и каталоги согласованными |

**Условие пересмотра ADR** (`methods/decision-keeper.md`): если появляется
серверная часть или внешняя LLM по умолчанию — ADR-2 и ADR-3 пересматриваются
вместе с §6 и NFR-7.

## 11. Домены и события (DDD)

**Bounded contexts:**

| Контекст | Ответственность | Что не входит |
|---|---|---|
| Модель требований | `P-*`, `J-*`, `UC-*`, `BR-*`, `FR-*`, `NFR-*`, `AC-*` | исполнение ролей и проверки |
| Артефакты прогона | файлы `output/<run-id>/` и их состав (FR-2) | смысл требований |
| Гейты и машинные проверки | `check_run`, `check_dor`, `check-sync`, `check-cross-refs` (FR-5) | правка требований за автора |
| Eval-обвязка | набор кейсов, mock, целевой замер (UC-8) | продуктовая логика заказчика |
| Промпты и роли | `prompts/roles/*.md`, схемы ответов (FR-11) | данные прогона |

**Контракты между контекстами:**

- `ARTIFACT { id, run_id, path, kind }` — модель требований → артефакты;
- `GATE_RESULT { id, run_id, gate, status, missing }` — гейты → артефакты;
- `FINDING { id, run_id, kind, status, source }` — валидация → eval и план.

**Агрегаты и инварианты:**

- `REQUIREMENT` держит инвариант «статус меняется только через гейт» (FR-5);
- `RUN` держит порядок этапов: BA-gate → SA-gate → Spec-gate (FR-4);
- `FINDING` не может быть закрыт без записи в `hallucination-log` (FR-12).

Питает: `diagrams/domain-map.mmd`, `diagrams/event-storming.mmd`.

## 13. AI / RAG

- **RAG:** не применим. Внешняя LLM запрещена по умолчанию **[допущение: Q-4]**,
  векторного хранилища и корпуса для retrieval нет — раздел `rag-pipeline` и
  `vector-schema` в этом прогоне не строятся.
- **Контекст роли:** собирается из промпта роли и входов, без поиска по корпусу;
  схема ответа задаётся только промптом роли (FR-11).
- **Цикл агента:** чтение промпта → планирование → вызов инструмента →
  наблюдение → ответ по схеме (UC-7), см. `diagrams/agent-workflow.mmd`.
- **Обратная связь:** прогон → `findings.jsonl` → eval или целевой замер →
  правка промпта или откат (UC-8), см. `diagrams/feedback-loop.mmd`.
- **Model selection и eval metrics:** таблица моделей и замеры —
  `docs/evaluation/README.md`; правило «измеряем только то, что оптимизируем»
  (целевой замер вместо полного прогона).

Питает: `diagrams/agent-workflow.mmd`, `diagrams/prompt-flow.mmd`,
`diagrams/feedback-loop.mmd`.

## 14. Инфраструктура и сеть

- **Зоны доверия:** клиент (редактор) — недоверенная входная зона; рабочая
  станция с репозиторием — доверенная зона (роли, гейты, артефакты);
  внешние — локальная LLM по HTTP на петле, `mmdc`, git-remote. См.
  `diagrams/c4-deployment.mmd`.
- **IaC:** не применим — развёртывания нет, установка через `uv` и `npm`.
- **Сеть:** исходящий трафик только к git-remote и локальному Ollama
  **[допущение: Q-4]**; внешняя LLM требует отдельного решения.

Раздел `network-topology` и `iac` в этом прогоне не строятся: инфраструктуры
как кода у фреймворка нет.
