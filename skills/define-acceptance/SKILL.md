# Skill: критерии приёмки с негативным сценарием

## Когда использовать

Требования валидны (`skills/detect-contradictions/SKILL.md` пройден), и их
пора передавать в разработку и QA. Применяется на стадии System analysis до
SA-gate. Один `UC-*` или `FR-*` за заход.

## Что делать

1. **Возьми один `UC-*` или `FR-*`.** Не пиши критерии «на всю систему».
2. **Позитивный сценарий.** `Given` — состояние, `When` — действие,
   `Then` — наблюдаемый результат. Присвой `AC-N`.
3. **Негативный сценарий.** То же действие при ошибке: отказ, таймаут, нет
   прав, пустой ввод, недоступный внешний сервис. Присвой отдельный `AC-N`.
4. **Проверь наблюдаемость.** `Then` — то, что можно увидеть в ответе, логе,
   метрике или состоянии. «Корректно обработано» — не наблюдаемо.
5. **Убери vague-слова.** «Быстро», «удобно», «правильно», «качественно»,
   «эффективно» заменяются числом или конкретным результатом.
6. **Заполни колонки** «Критерий приёмки (BDD)» и «Негативный сценарий
   (BDD)» в `functional-requirements.md`; свяжи `AC-*` с `UC-*` в
   `traceability-matrix.md`.

## Чего нельзя

- Оставлять только happy path.
- Писать критерий без `AC-*` или без наблюдаемого `Then`.
- Прятать негативный сценарий в прозе вне таблицы.
- Считать «не падает» критерием: падение без ошибки — тоже поведение.

## Метрики / проверка

- У каждого `FR-*` есть минимум один позитивный и один негативный `AC-*`,
  когда колонки присутствуют в шапке.
- В критериях нет vague-слов.
- `check_run.py` проверяет заполненность негативной колонки и стоп-слова.
