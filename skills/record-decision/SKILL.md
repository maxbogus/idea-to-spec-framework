# Skill: архитектурное решение (ADR)

## Когда использовать

Принимается решение, влияющее на стоимость, стек, интеграции, безопасность
или необратимость миграции. Стадия Architecture, до Spec-gate. Один ADR —
одно решение.

## Что делать

1. **Контекст.** Какая сила требует решения: ограничение, риск, NFR или
   интеграция. Без контекста решение не пересматривается осознанно.
2. **Статус.** `Proposed` / `Accepted` / `Deprecated` / `Superseded`. Статус
   показывает, действует решение или уже заменено.
3. **Минимум две альтернативы.** Для каждой — плюсы и минусы. Один вариант
   означает, что выбора не было; так и напиши, если это правда.
4. **Решение.** Что выбрано и почему именно этот trade-off.
5. **Последствия.** Что выиграли, чем пожертвовали, что станет дороже:
   эксплуатация, найм, миграция, стоимость.
6. **Условие пересмотра.** При каком изменении решение пересматривается
   (`methods/decision-keeper.md`).
7. **Запиши ADR** в `spec.md §10`; из C4/§9 поставь ссылку на `ADR-*`.

## Чего нельзя

- Оставлять одну альтернативу или пустые плюсы/минусы.
- Писать «выбрали лучший» без критерия выбора.
- Скрывать необратимость: миграция данных и смена протокола — последствия.
- Менять статус без причины и даты пересмотра.

## Метрики / проверка

- У каждого `ADR-*` есть статус, ≥2 альтернативы и последствия.
- На каждое решение из C4/§9 есть `ADR-*`.
- `check_run.py` проверяет ADR-таблицу, когда в шапке есть колонка «Статус».
